# Unified RAG

I built this multimodal RAG app to see how far I could push Google Gemini alongside ChromaDB. It handles text, images, audio, and video directly without relying on heavy OCR pipelines. 

[Live demo](https://unified-rag.streamlit.app/) — no signup, no API key. Hit **Load 6 sample charts** in the sidebar and ask it something. Uploads are capped there so one visitor cannot exhaust the container; clone the repo to run it without limits.

The demo runs on a key the deployment supplies (`GOOGLE_API_KEY` in Streamlit secrets, see `.streamlit/secrets.toml.example`). Paste your own key in the sidebar and it takes priority. With no key configured anywhere, the app falls back to asking each visitor for one, which is how it behaves on a fresh clone.

## What's inside

- **Gemini Embedding 2**: Maps everything (text, charts, audio clips, video frames) into a single vector space.
- **Gemini 3.6 Flash**: Reads the retrieved chunks and generates the final answer, dropping to `gemini-3.5-flash-lite` when `DEMO_MODE` is on. The whole app was on the 2.5 line until 2026-08-01, when that generation started returning 404 to newly issued API keys — model ids now live in one place (`app/gemini.py`) so the next retirement is a one-line fix.
- **ChromaDB**: Local vector storage. It's fast enough for what I need and doesn't require setting up cloud infrastructure just to test an idea.
- **Google File Search (Managed RAG)**: I added this to bypass local limits when dealing with massive document dumps. It offloads the hassle of ingestion squarely to Google Cloud.

## How it works

1. **Upload**: You drop files in. The app either embeds them locally into Chroma (using `gemini-embedding-2-preview`) or pushes them straight to an ephemeral Google File Search store. Local uploads go through hashed file storage under `.unified_rag_store/` instead of stuffing raw bytes into Chroma metadata when possible.
2. **Search**: You ask a question. The backend can route to Google File Search, or run hybrid local retrieval: dense Chroma search fused with BM25 keyword ranking via Reciprocal Rank Fusion (RRF).
3. **Answer**: the answer model gets the top retrieved chunks (not just the first hit) with source IDs like `[S1]` and `[S2]` so citations actually mean something.

What the tables say, question type by question type:

- **Keyword questions go to BM25.** BM25 and plain hybrid find every keyword question in the top five. An article number or a name is a literal token, and BM25 matches tokens no matter how much text surrounds them. A dense vector has to average one identifier into a whole chunk's meaning, so dense alone misses some. The reranker gives one back (g045): the chunk with the right article number is worded differently from the question, and the cross-encoder ranks it down.
- **Paraphrase questions go to dense.** BM25 almost never finds them, because those questions avoid the source's words by design. Plain RRF then gives BM25's ranking the same weight as dense's, so on these questions the right chunk sinks behind BM25's word-overlap matches. That's the gap between Dense and Hybrid (RRF) in the paraphrase column. The reranker reads the question against each candidate and recovers most of it, but not all. On g067, g069, g075 and g076 the gold chunk is in its candidate pool and it still ranks it below the top five, so Hybrid + rerank trails Dense alone on paraphrases.
- **The reranker is the change that pays.** The reranked configs have the best hit@1 and MRR@10, and the rerank step takes a fraction of the time generation does. HyDE reorders many rankings but rarely changes the top three chunks, so it buys nothing measurable here and adds more retrieval latency than the reranker does.
- **One context chunk looks better than it is.** Answers get faster, cheaper and more faithful, and they stay more faithful even on the questions judged under both settings. But the model refuses far more answerable questions, because the one chunk it sees often isn't enough. Faithfulness alone would pick this config, which is why it's reported next to false refusals.

The next retrieval change worth testing is fusion weighted by question type: keep BM25's pull on identifiers without letting it bury dense hits on reworded questions. The paraphrase column is the number it has to move.

An earlier, smaller synthetic benchmark still lives in `tests/test_ablation.py` as a regression test. It runs offline from cached embeddings.

## Features that matter

- **It takes basically anything**: PNGs, JPGs, MP3s, WAVs, MP4s, MOVs, and regular PDFs.
- **Hybrid Routing**: You don't have to manually pick the backend. Gemini Flash runs a sub-second check to figure out if your query belongs in the local vector store or the managed Google backend.
- **Hybrid local retrieval**: Dense vectors plus BM25/RRF so exact keywords and serial numbers are less likely to disappear.
- **Multimodal embeddings**: Per-image captions (including an optional auto-caption path), image+text interleaved embeddings, PDF overlap chunking with extracted text for search, timestamped audio chunks decoded from MP3, and scene-based video frame sampling that skips near-duplicate frames.
- **Speech-to-text**: Audio files and the audio track inside videos get transcribed with Gemini (there's a sidebar toggle), and each video frame inherits the transcript of the window it falls in. Spoken words become searchable.
- **One source per file**: Every uploaded file is one sidebar entry and one registry row that tracks all its chunks, so deleting it cleans up every chunk's blobs. Re-uploading the same bytes is skipped via a content hash.
- **Source registry**: A JSON registry tracks file paths, page ranges, timestamps, captions, and Chroma IDs, written atomically and rebuilt into the sidebar on restart.
- **Citation click-through**: Answers cite `[S1]`, `[S2]`, etc.; opening one shows the exact cited chunk's pages or frame and seeks audio/video to the matched timestamp.
- **Image queries**: You can upload an image instead of typing a question. The app hits ChromaDB's HNSW index to find visually or semantically similar content.
- **Browser TTS**: I threw in a quick Web Speech API integration so the app can read answers out loud.
- **Adjustable MRL**: You can slide the embedding dimensions between 3072, 1536, and 768.

Most of the non-UI logic lives in helper modules now (`rag_core.py`, `media_ingest.py`, `storage.py`, `source_registry.py`, `eval_harness.py`, and `app/gemini.py`) so I can unit test retrieval and ingest without launching Streamlit.

## Running it locally

You'll need Python 3.10 or higher.

```bash
pip install -r requirements.txt
streamlit run app.py
```

You just plug your Gemini API key into the sidebar when the app loads. I set it up specifically to only hold your key in session memory. There are no accounts, and it doesn't save your key to disk.

For heavy usage, you can connect it to a hosted Chroma Cloud instance by dropping in your tenant details. Otherwise, it defaults to creating a `./chroma_db` folder locally.

There are tests under `tests/` if you want to sanity-check helpers (`python3 -m unittest discover -s tests`). PDF tests skip automatically when PyMuPDF isn't installed.

## Retrieval from the command line

Retrieval and answering live in `rag/pipeline.py` now, behind one `Config` (mode `dense`, `bm25` or `hybrid_rrf`, plus `rerank`, `hyde`, `top_k`, `context_k`). The Streamlit app and the CLI both call it, so anything I measure from the terminal is the code the app runs.

The benchmark corpus is fixed: the EU AI Act as published in the Official Journal, plus a set of Wikipedia articles pinned by revision id, all listed in `corpus/manifest.json`. The extracted text is committed under `corpus/docs/`, so chunk boundaries can't drift when Wikipedia re-renders an old revision. Figures are indexed as image + caption chunks; the images themselves are downloaded, not committed.

```bash
uv pip install -r requirements.txt
uv run python -m rag.corpus fetch            # download raw sources and figures (text is already committed)
uv run python -m rag.index build             # embed into .eval_index/, asks before spending API calls
uv run python -m rag.cli "Which AI practices does Article 5 prohibit?" --mode hybrid_rrf --rerank
```

The CLI prints each hit's chunk id with its dense, BM25, RRF and rerank scores. Add `--answer` for a cited answer, or `--hyde` to embed a drafted answer alongside the question. Reranking is a local cross-encoder (`ms-marco-MiniLM-L-6-v2` through fastembed's ONNX runtime), so it needs no API key.

Chunk ids are a hash of document id, page (or section), character offset and kind, so rebuilding the index from the same text gives the same ids. `uv run python -m rag.index verify-stable` proves it: it deletes the index, rebuilds it and checks every ranking comes back identical.

## Golden set

The eval questions in `eval/golden.jsonl` were drafted by an LLM, checked by two other LLMs, and approved by me. Nothing goes into the set without that approval.

1. `uv run python -m eval.draft_questions` samples chunks across every document in the corpus (seeded, so the sample is reproducible) and asks `gemini-3.6-flash` for one question per chunk, plus the answer and a verbatim evidence quote. Question types are factual lookups, exact-identifier questions (article numbers, names, codes), paraphrases that avoid the source's wording, two-source multihop questions, and questions the corpus can't answer.
2. Gold chunk ids come from where the evidence quote actually sits in the corpus, not from which chunk happened to be sampled. Chunks overlap, so a quote in the overlap makes both chunks gold. A quote that can't be found verbatim gets flagged rather than guessed. Legal text restates itself (a recital and its article, one amendment applied to several regulations), so an exact copy of the quote anywhere else in the corpus is gold too, and near-copies are shown during review so I can add them if they answer the question. Otherwise a retriever that finds the article instead of the recital would be scored as a miss.
3. Two independent LLM passes (Claude Haiku 5.5 and Claude Sonnet 5.5, spot-checked by a larger Claude model) proposed keep, edit or drop for every candidate, with a one-line reason each (`eval/review_suggestions.jsonl`). I decided the first rows one at a time in `uv run python -m eval.review`, then read through the remaining suggestions and approved them as a batch, leaving out multihop pairs the two models disagreed on. `eval/review_log.jsonl` marks which rows were decided individually and which by batch approval. Kept rows are appended and never rewritten.

Known bias in this method: each question is written by a model reading one chunk, so questions lean toward that chunk's vocabulary. That flatters lexical and dense retrieval of exactly that chunk. The paraphrase type pushes against it (candidates whose wording overlaps the source too much are flagged), but doesn't remove it. The drafter is also the same model family as the answer generator, so generation metrics are judged by a model from a different family. Embeddings are cached in `.cache/`, which makes a rebuild free. `uv run python -m rag.index verify-stable` checks both: it deletes the index, rebuilds it and confirms every ranking comes back identical.

## Metrics

`uv run python -m eval.run --config <name>` runs the golden set through one config in `eval/configs/` and writes `results/<name>.json`: every question's ranked chunk ids, answer, scores and latency, plus totals overall and per question type.

- **Retrieval** (answerable rows only): hit@1, hit@3 and hit@5 (is any gold chunk in the top k), MRR@10, and recall@5, which matters for multihop questions with two gold chunks. Retrieval is scored at depth 10, and the answer sees the top `context_k` hits.
- **Citations**: the share of `[S1]`-style citations that point at a gold chunk. Answers with no citation are counted separately, not as correct. A cited chunk that supports the claim but isn't in the gold set counts as wrong, so this is a lower bound.
- **Faithfulness and answer relevancy**: DeepEval's metrics, judged by `gpt-4.1-mini` version `2025-04-14` on Azure AI Foundry at temperature 0. The judge is a different model family from the `gemini-3.6-flash` generator. Both run on answerable questions the system didn't refuse.
- **Refusals**: on unanswerable questions, how often the system says the sources don't contain the answer. On answerable ones, how often it refuses anyway. The judge decides what counts as a refusal.
- **Latency, tokens and cost**: p50 and p95 per stage (query embedding plus search, rerank, generation), with cost per query from `eval/prices.json`. Judge cost is reported separately, since it isn't part of answering.
- **95% bootstrap intervals** for hit@5 and faithfulness, because 100 questions is a small sample.

Every API call (answers, judge verdicts, query embeddings) is cached in `.cache/` with the latency and tokens of the original call. A rerun is free and reports the same numbers. The benchmark's dense search is an exact cosine scan instead of Chroma's approximate HNSW index. HNSW sometimes dropped a true neighbour from the candidate pool, a different one from process to process, so a rerun could change the score with nothing changed. The judge needs `JUDGE_ENDPOINT` (a Foundry resource) and an `az login` session with access to it; `--no-judge` skips it.

What these metrics miss: faithfulness only checks that the answer agrees with the retrieved text, so a faithful answer built on the wrong chunk still scores well. That's why it's reported next to hit@k and citation correctness, not alone. Figures reach the judge as their caption, since DeepEval's judge here is text-only, so an answer read off the image itself can score lower than it deserves. The judge also makes mistakes of its own. Reading through the flagged rows turned up answers it called refusals that weren't, and near-verbatim answers it marked unfaithful. I kept DeepEval's default prompts rather than tune them until the scores looked better, so treat single-row judge scores as noisy and read the totals with their intervals.

## Notes to self: what's left

My professor reviewed the codebase a while back and pointed out a pile of real embarrassments. Most of that list is gone now. Retrieval is hybrid BM25+RRF with top-K context. Audio and video get transcribed. MP3 decodes properly, re-uploads dedupe by content hash, each file is one source row, citations seek to the right spot, and the corpus survives a restart.

Fixed since the last version of this list:

- **Grow the eval set**: done. The small regression set is now a reviewed golden set on a fixed public corpus, with gold chunk ids and a recorded review. See [Golden set](#golden-set).
- **Cross-encoder reranking**: done and measured. A local `ms-marco-MiniLM-L-6-v2` reranker is one of the configs in [the results](#does-the-hybrid-retrieval-actually-help), with its latency cost next to its gain. The caveat still holds: the benchmark is mostly text, so it says little about how a text-only reranker handles charts and video frames.

Still open:

- **Weighted fusion**: plain RRF gives both rankings equal weight, even on a question where one of them is useless. Weighting the arms by query type is the next retrieval change worth trying, and the per-type table is the baseline to beat.
- **Judge agreement**: the generation judge makes visible mistakes. A small hand-labelled check set, plus a script that reports judge agreement, would put a number on how far to trust faithfulness.
- **Tracing and a CI gate**: per-query traces, and a pull-request check that fails when retrieval or faithfulness drops.
- **Transcription cost**: speech-to-text is one Gemini call per chunk. Fine for short clips, rough for a long video. I want a batch path or a per-file cap before heavy use.
- **Semantic PDF chunking**: overlap page windows are in place. `semchunk` is worth trying now that the benchmark can show whether chunk boundaries cost anything.
- **The cutting-edge stuff**: ColPali (treats pages as image patches, skips OCR), ColBERT-style late interaction, RAPTOR tree summarization, full agentic RAG. Interesting, each a real dependency and a real architecture change. Only worth it if this becomes a product or a research demo, not before.
